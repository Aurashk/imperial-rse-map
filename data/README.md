# Map data

The map is driven entirely by the JSON files in this folder. No build step is
needed: edit a file, push, and the site updates. Run
`node scripts/validate-data.mjs` before committing; CI runs the same check and
will not deploy broken data.

| File | What it holds | How it is maintained |
|---|---|---|
| `departments.json` | Faculties (containers) and departments (nodes) | By hand |
| `activities.json` | Central RSE team offerings and engagements with departments | By hand, or exported from the team's records |
| `software.json` | Research software from the Imperial Research Software Directory | Generated by `scripts/import_research_software.py` |
| `software-attributions.json` | Rules attributing software to departments | By hand |

## `departments.json`

```jsonc
{
  "groups": [
    { "id": "engineering", "name": "Faculty of Engineering", "shortName": "Engineering", "kind": "faculty" }
  ],
  "departments": [
    {
      "id": "physics",                 // lower-case, digits, "-" or "_"; used in URLs (#department=physics)
      "name": "Department of Physics",
      "shortName": "Physics",          // node label
      "group": "natural-sciences",     // a group id
      "url": "https://www.imperial.ac.uk/physics/",
      "verify": true                   // optional: flags the entry as needing confirmation
    }
  ]
}
```

## `activities.json`

`offeringTypes` defines the categories. **Their order fixes their colours** (the
palette is validated for colour-vision deficiency in that order), so append new
types rather than inserting them; colours live in `css/styles.css` as
`--type-<id>`.

`services` lists the team's standing offers, shown on the overview panel.

Each entry in `activities`:

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Unique; used in URLs (`#activity=<id>`) |
| `title` | yes | |
| `type` | yes | An `offeringTypes` id |
| `departments` | yes | One or more department ids |
| `start`, `end` | no | `YYYY-MM`. Omit `end` for ongoing work. Undated activities appear only under "All years" |
| `status` | no | `active`, `planned` or `completed`; omitted means "not recorded" |
| `sessions` | no | Integer; used for code surgeries |
| `summary`, `url` | no | |
| `source.kind` | yes | `public` (citable public source), `internal` (team records) or `mock` (placeholder) |
| `source.ref` | for `public` | Link to the evidence |
| `source.confidence` | no | `high`, `medium` or `low` – how sure the department attribution is |
| `source.note` | no | Free text explaining the attribution |

Mock records exist only to show the format. Replace them, keeping `source.kind`
honest, and they disappear from the "Include mock data" toggle automatically.

### Suggested sources for real activity data

- Code surgery bookings (department of the person booking, date, count).
- Project records kept under the team's SOP for project work.
- Open-source booster applications and outcomes.
- Training attendance by department.
- The Research Software Community newsletter for sprints and events.

## `software.json`

Regenerate with:

```bash
python3 scripts/import_research_software.py
```

The script reads the directory's `repos.csv`, adds public GitHub metadata
(set `GITHUB_TOKEN` to avoid rate limits), applies
`software-attributions.json`, and drops contact names and e-mail addresses.
Repositories it cannot attribute are listed at the end of its output and on the
map's research-software overview. To fix one, add a rule to
`software-attributions.json` – under `owners` for a whole GitHub account, or
under `repos` for a single repository – and re-run the script.

On the map, each department's **ring** counts its packages with no recorded
RSE involvement. When the RSE team has worked on a package, add
`"rseInvolved": true` to its rule under `repos` and re-run the script; the
package then leaves the ring and is tagged "RSE team involved" instead.
